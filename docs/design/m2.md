# M2 — the assertion machinery reaches the response

> Status: design · 2026-08-02 · the milestone that makes open-ticket M5 fully expressible.

## Problem

M1 built an honest measuring instrument. What it cannot do is **look at what came back**.

`TransportResponse` carries a status and nothing else; the body is read (for honest timing) and
discarded. A scenario sends one request for its whole lifetime. Nothing user-written runs per
response. So of open-ticket's four contract runs, M1 can express one and a half:

| #   | Run                                   | M1     | Missing                                                                                                        |
| --- | ------------------------------------- | ------ | -------------------------------------------------------------------------------------------------------------- |
| 1   | **The stampede** — N buyers, one seat | partly | "exactly one 201, N−1 conflicts" is a claim about _statuses_, provable today only after the fact in `teardown` |
| 2   | **Hot show, many seats**              | no     | a distinct seat per buyer — the engine carries one request per scenario                                        |
| 3   | **Read fan-out under write load**     | yes    | —                                                                                                              |
| 4   | **Projection lag at peak**            | no     | `behindMs` comes out of a **response body** the tool throws away                                               |

The contract asked for three things by name that M1 left out, and they are the same three:
**per-response checks with names**, **custom counters merged across workers**, and thresholds over
them. `metrics/` has had `Counters` and `Checks` since M1's PR 2 — merged, snapshot-safe, tested to
the point of mutation. Nothing user-facing has ever been able to reach them. M2 is the wiring.

**M2 does not do SSE.** Contract run 5 (M+ concurrent event-stream readers) needs a streaming,
long-lived request mode rather than request/response — a genuinely different engine shape, and
open-ticket said in writing that it is not waiting on it. It is M3.

## Scope

**In:** the response body and headers reaching user code; per-scenario `checks`; `onResponse` with
custom counters and trends; per-request variation via a global dispatch ordinal; per-scenario
counters and checks on the threshold-facing summary; a checks table in the markdown report; check
failures surfacing on the live dashboard.

**Out:** SSE/streaming (M3), distributed workers, protocols beyond HTTP(S) — the M1 non-goals stand.

## Decisions specific to M2

### D2-01 — The response carries status, headers and text, always

Every check and `onResponse` receives `{ status, headers, text }`. Not opt-in, not lazy.

The body is **already read**: `http-transport.ts` drains it with `arrayBuffer()` so the measured
window covers the whole response rather than stopping at the headers. The only new cost is decoding
those bytes to a string and holding it for the duration of one callback. That is bounded by
`maxInFlight` and freed immediately, and it buys an API with no flag to forget and no `undefined`
body to explain.

The two rejected shapes are worth naming because both look cheaper than they are. **Opt-in
(`readBody: true`)** costs nothing at runtime and costs a user their first debugging session when a
check reads `undefined`. **A lazy `await response.text()`** pays only on use, but the read would
land _outside_ the measured window — so latency would silently stop meaning what it means
everywhere else in the tool, which is the one thing this repo will not trade.

`text` is a string, not parsed JSON. Parsing costs on the hot path and throws on the one response
that isn't JSON, which is exactly the response you most want a check to catch.

### D2-02 — `request(state, index)`, where `index` is the run's ordinal, not the shard's

The request builder gains the dispatch ordinal, so run 2 is `seats[index % seats.length]`.

The subtlety is which ordinal. `mergedSchedule` numbers dispatches from 0 **within each shard**, so
four workers would each build request 0, 1, 2 — and "N buyers, N distinct seats" would quietly
become four buyers per seat, which is the exact bug the run exists to detect. `schedule-split.ts`
already documented the recovery when it wrote the stride: the global ordinal is
`shardIndex + localIndex * shardCount`, exact by construction because the stride _is_ that mapping.

Two costs, both accepted and both worth stating:

- **A request object per dispatch** rather than one per scenario. Allocation on the hot path, and
  it is the honest cost of the feature — a client that sends a different body each time really does
  build it each time.
- **The body-encoding memoisation in `http-transport.ts` stops helping.** It is keyed on the request
  object, and now every dispatch has a new one. That memo was added in M1 to stop a _constant_ body
  being re-serialised on every send; with varying requests, encoding once per distinct request is
  exactly right, so the WeakMap keeps being correct and simply stops hitting.

`request(state)` keeps working — the second parameter is optional to the user, present always.

### D2-03 — Counters and checks are per scenario, and only per scenario

Thresholds read `s.scenarios[0].counters.reserved201`, not `s.counters.reserved201`.

D1-06's worked example promised the short top-level form. It was written before D1-05 established
that a run holds several concurrent scenarios, and the two cannot both be right: merging counters
across scenarios means a `reserved201` in the write scenario and a `reserved201` in the read
scenario silently add together. That is the class of quiet wrongness this repo has refused at every
turn, and a convenience view would be the form everyone reaches for. The design doc's example is
corrected rather than the storage bent to fit it.

`metrics/` already namespaces per scenario, so this is also the shape that needs no translation
layer — the summary projects what the registry holds.

### D2-04 — A check that throws is counted, not fatal; a check that fails is just a failure

User code now runs on the hot path, per response, inside a worker. Two failure modes, deliberately
different:

- **A check returning `false`** is the point of the feature: counted as a failure against its name,
  reported as a row, available to thresholds.
- **A check or `onResponse` that throws** is a broken check. It is counted separately, the run
  continues, and the run is failed at the end with the check named — the same treatment a broken
  _threshold_ predicate gets (M1's D1-06), and for the same reason: a bug in the assertion must not
  be reported as the target violating an invariant, and must not abort a twenty-minute run either.

A check that throws on every response would otherwise fill a run with noise; the count is what makes
it visible without drowning the report.

### D2-05 — The report grows a checks table; the dashboard surfaces failures live

The contract asks for a checks table by name. A check that has started failing is also the thing a
watcher most needs to see _during_ a run — waiting until the summary to reveal that every response
has been failing `noDoubleSell` for eight minutes is the same mistake as hiding drops, which the M1
dashboard already refuses.

## Shape

```
src/
├── engine/
│   ├── ports.ts            # TransportResponse gains headers + text
│   ├── http-transport.ts   # decode the bytes it already reads
│   ├── dispatcher.ts       # run checks/onResponse per response, count throws
│   └── schedule.ts         # carry the global ordinal through the shard
├── config/
│   └── types.ts            # checks, onResponse, request(state, index)
├── report/                 # checks table
└── tui/                    # failing checks, live
```

## Sub-PR breakdown

1. **docs — this design**, plus the `docs/decisions.md` entries for D2-01…D2-05.
2. **feat(engine) — the response reaches user code.** `TransportResponse` gains `headers` and
   `text`; the transport decodes what it already reads. Tests: a body is delivered intact, a
   non-UTF8 body does not throw, headers are lower-cased once, and the measured window is unchanged
   (the decode is inside it, and that is stated).
3. **feat(config, engine) — checks and `onResponse`.** Config types and validation; the dispatcher
   runs them per response into the scenario's own `Checks`/`Counters`/`Trend`; a throwing callback
   is counted and the run survives. Tests: pass/fail tallies merge across workers, a throwing check
   is counted once per response and named at the end, and a check never sees a response that failed
   at transport level.
4. **feat(engine) — per-request variation.** The global ordinal through `mergedSchedule` and
   `shardScenarios`; `request(state, index)`. Tests: the union of ordinals across W shards is
   exactly `0..N-1` with no repeats — the property run 2 depends on — plus the single-shard case.
5. **feat(cli) — counters and checks on the summary, and in thresholds.** Per-scenario projection,
   frozen like the rest; a broken check fails the run with the check named.
6. **feat(report, tui) — the checks table, and failures live.**
7. **docs — README, the reality-gate evidence, and M2 marked complete.**

## Verify for real (gate two)

The existing four runs must keep passing unchanged — the response now carries more, and the numbers
must not move.

New, and the point of the milestone:

- **A check that fails is counted, not lost.** Point a run at the reference target with a check that
  fails on every response; the run must report exactly `N` failures and fail its threshold.
- **Counters merge across threads.** A counter incremented once per response, across 4 workers,
  must equal the response count exactly — the same claim `metrics/` proves in isolation, now proven
  through the user-facing path.
- **The namesake run, for real.** Against the open-ticket-shaped target used in M1's README
  verification: 500 buyers, one seat, `counters.reserved201 === 1` and `checks.oneWinnerOrConflict
.failed === 0` — the contract's run 1, asserted _during_ the run rather than only in `teardown`.
- **Distinct seats.** 500 buyers across 500 seats through 4 workers: every ordinal used exactly
  once, verified against the target's own record of which seats it was asked for.

## Deferred (not M2)

SSE / long-lived streaming requests and the connection accounting they need (M3, contract run 5).
Distributed workers, protocols beyond HTTP(S), a cloud service, a scripting DSL — the M1 non-goals
are unchanged.
