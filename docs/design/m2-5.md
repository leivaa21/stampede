# M2.5 — usable by someone who is not its author

> Status: design · 2026-08-03 · the milestone between M2 and SSE.

## Problem

M2 finished the assertion machinery and proved it against a referee. Two things stop stampede
being a tool anyone else can pick up, and both were found by M2's own review rounds rather than
guessed at:

1. **It is unpublished.** The README's install block leads with `git clone`.
2. **It fails a legitimate config.** A counter per endpoint path — an entirely reasonable thing to
   want — hits `MAX_DISTINCT_TALLIES` and the run fails telling the user to use fewer names. That
   is the correct behaviour given the caps (a refusal nobody counts is a silent hole), but "use
   fewer names" is a diagnosis without a remedy, because there is no bounded way to say what they
   were trying to say.

A third gap is smaller and of the same family: **`request()` is documented as pure and nothing
checks it.** Every worker gets its own structured clone of the setup state, so a builder that
consumes shared state — `state.seats.pop()` — hands four threads the same four values and produces
a run whose numbers are wrong in a way no threshold would catch.

And one piece of process debt: **gate two never re-runs.** The README publishes numbers from it and
calls it a manual milestone gate. M2's review found a published figure that was two milestones
stale precisely because nothing re-measured it.

## Scope

**In:** declared-key counters; deep-frozen setup state; a nightly non-blocking gate-two workflow;
release preparation for `0.2.0`.

**Out:** SSE and long-lived streaming — that is M3, and it is a second scenario lifecycle rather
than a feature on this one. Distributed workers, protocols beyond HTTP(S): the M1 non-goals stand.

**Not in this milestone's gift:** the `npm publish` itself. It needs leivaa's credentials, and
publishing is not cleanly reversible, so this milestone prepares the release and stops.

## Decisions

### D25-01 — Bounded counters declare their key space; they do not approximate

**Decision.** A scenario may declare a **keyed counter** with a fixed key list. `record.countKeyed(
name, key)` increments the slot for `key`, or an implicit `other` when the key was not declared.

```ts
scenarios: {
  reads: {
    profile: constantRate({ ratePerSecond: 200, durationMs: 10_000 }),
    request: (state) => ({ url: state.url }),
    counters: {
      byStatus: { keys: ["2xx", "4xx", "5xx"] },
    },
    onResponse: (res, record) => {
      record.countKeyed("byStatus", bucketOf(res.status));
    },
  },
}
```

Storage is the counter map it already was — `byStatus.2xx`, `byStatus.4xx`, `byStatus.5xx`,
`byStatus.other` — with every slot **reserved before the run starts**, the same mechanism the
engine's own counters and the per-check broken tallies use. The summary projects them back into the
shape the config declared, so a threshold reads
`s.scenarios[0].keyedCounters.byStatus["5xx"] === 0` rather than a stringly-joined key.

**Why not top-N.** The obvious answer is a space-saving or Misra-Gries sketch: keep the N heaviest
keys, fold the rest into `other`, no advance knowledge needed. It is the wrong answer _for this
repo_. Those sketches merge **approximately and order-dependently**, and D1-02 exists because
"published numbers must not depend on which worker finished first" is the property the whole
worker architecture rests on. A metric kind that quietly broke it would be the most expensive
inconsistency in the codebase — and it would live in `metrics/`, the module whose docblock says it
is the most-tested code in the repo because every published number comes out of it.

Declaring the keys costs the user advance knowledge and buys back an exact, associative,
commutative merge with no new algorithm, no new failure mode, and no second answer to "what does a
counter mean".

**Why `other` is implicit and always present.** A key that was not declared has to go somewhere, and
dropping it would be the silent hole `metrics/validate.ts` refuses. Making the bucket implicit means
a config cannot forget it, and a non-zero `other` is itself the signal that the declared key space
is wrong.

**Rejected: `record.count("byStatus." + key)` with a declared prefix.** Same storage, but the API
would let a typo'd prefix create an undeclared name that silently counts on its own until the cap
bites — which is the failure this decision exists to remove.

### D25-02 — The setup state is deep-frozen, at the worker's door

**Decision.** `worker-entry.ts` deep-freezes the setup state before handing it to `scenariosFrom`.
A `request()` that mutates it throws; the eager ordinal-0 call turns that into a message naming the
purity contract, and a mutation on a later ordinal is counted as `impureRequestCount` and fails the
run.

**Why in the worker, and at that door.** `structuredClone` does not preserve frozenness, so freezing
on the main thread would protect nothing — the worker's copy is the one a builder can reach. At the
_door_ rather than inside `scenariosFrom`, because that function is exported and a converter that
seals its caller's argument in place is a side effect its name and signature do not disclose.

**Why freezing rather than comparing two calls.** Calling `request(state, 0)` twice and comparing
would also catch a nonce — but it false-positives on a builder that legitimately varies on something
external, and it doubles a call the author was told runs once per dispatch. Freezing catches the
violation that actually happens, `state.seats.pop()`, with a message.

**Only plain objects and arrays are frozen**, and that is a correctness constraint. `Object.freeze`
_throws_ on a non-empty typed array, so a `Buffer` in the setup state — the canonical shape for an
authed API — killed every worker with a raw V8 string. Freezing a `RegExp` is quieter and worse:
`lastIndex` becomes non-writable, so a pure `re.test(...)` throws a message the matcher reads as a
purity violation. **Consequence, stated:** a `Map`, `Set`, `Date`, `Error` or typed array can still
be mutated and this will not catch it.

**A later-ordinal mutation gets its own count.** Folded into `requestErrors` it read as "9 not
built" and the run exited 0 — stampede refusing 90 % of its own load and reporting success.
`impureRequestCount` is a term of the dispatch identity and has its own run-failure message, because
"a check or onResponse threw" is the wrong sentence for a config with neither.

**Rejected: relying on the freeze alone.** CommonJS runs in sloppy mode, where a write to a frozen
object fails _silently_, so D25-02 enforces nothing there. `configUrlFor` refuses anything that is
not `.ts` or `.mts`, and separately anything Node would load as CommonJS — resolved from the nearest
`package.json` rather than from the extension, because a `.ts` file in a package without
`"type": "module"` is CommonJS too, and that is the shape a real user has.

### D25-03 — Gate two runs nightly, and cannot redden a pull request

**Decision.** A scheduled workflow runs `pnpm gate:two` and opens an issue on failure.
`workflow_dispatch` for running it by hand. It is not a required check on pull requests.

**Why not on every PR.** The gate's own claims are timing bands — run 1 asserts a p50 inside
48–65 ms, run 2 asserts a rate within 5 % — and a shared runner under load fails them for a
_correct_ change. A gate that cries wolf is a gate people learn to ignore, and this one is the
repo's evidence. The README says it is a manual milestone gate; wiring it as blocking would make
that sentence false.

**Why nightly rather than never.** M2's review found the README publishing an achieved rate from a
build two milestones old — the body read M2 added cost real per-response time and nothing
re-measured it. Evidence that never re-runs rots silently. Nightly catches that without letting a
slow runner block work.

## PR breakdown

1. **docs** — this design, plus the `docs/decisions.md` entries for D25-01…D25-03.
2. **feat(metrics, config)** — declared-key counters: `Counters` reservation, config validation,
   `record.countKeyed`, the summary projection, report and dashboard rendering.
3. **feat(config)** — deep-frozen setup state and the actionable message.
4. **ci** — the nightly gate-two workflow.
5. **chore(release)** — `0.2.0`, a changelog, and packaging verification. Publishing is leivaa's.

## What would prove it

Unit tests as usual, and specifically:

- A keyed counter merged across four real worker threads equals the same keys recorded into one
  registry — the D1-02 property, asserted for the new metric kind rather than assumed.
- An undeclared key lands in `other`, and `other` is never absent.
- A declared key space too large for the budget fails at **load**, with the arithmetic in the
  message.
- `state.seats.pop()` in a `request()` fails at startup with a message naming the purity contract,
  not with a `TypeError` about a sealed array.
- Gate two still passes 39/39 — the new code touches the counter path the contract runs depend on.
