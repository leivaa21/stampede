# M1 — the honest load engine, with assertions

> Status: design · 2026-07-30 · the milestone that unblocks open-ticket M5.

## Problem

open-ticket's headline claim is **zero double-selling under load**. Publishing that claim needs an
instrument that can do something a benchmarker cannot: **assert an invariant about a whole run** and
fail CI when it breaks. "p99 was 180ms" is a number; "exactly one of 500 concurrent buyers got a
201" is a proof.

The consumer-side spec was written first — open-ticket's M4 design, _"The load contract stampede
must satisfy"_ (in review as `leivaa21/open-ticket#18` at the time of writing, so the table below is
the self-contained version) — so this tool is designed against a real customer instead of a guess.
Four runs have to be expressible:

| #   | Run                                                                   | The claim under test                                              |
| --- | --------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 1   | **The stampede** — N buyers, one seat, all at once                    | exactly one 201, N−1 conflicts, zero double-sells                 |
| 2   | **Hot show, many seats** — N buyers across one show                   | successful reservations = distinct seats held; retry rate bounded |
| 3   | **Read fan-out under write load** — heavy `GET`s while writes contend | read p99 holds while writes contend                               |
| 4   | **Projection lag at peak** — sustained write ceiling                  | how far `behindMs` falls behind                                   |

Reading those as requirements rather than scenarios is most of the design:

- Run 1 is a **burst**, not a rate — N requests dispatched at t=0.
- Runs 1 and 2 need **named checks** and **custom counters merged across workers**, plus
  **setup/teardown with shared state** (setup creates the show and hands every virtual user the same
  `showId`; teardown re-reads the seat map and proves the invariant _after_ the storm).
- Run 3 needs **two scenarios running concurrently in one run**, each with its own arrival profile
  and its own latency percentiles. Read p99 is meaningless if it is averaged with write p99.
- Run 4 needs a user-recordable **numeric distribution**, not just a counter — `behindMs` sampled
  over time is a trend, and its max is the answer.
- All four need **thresholds that set the exit code**, or the numbers never gate anything.

## Scope

**In:** the open-loop engine with arrival profiles, worker-thread parallelism, mergeable
histograms/counters/checks, TS config loading, setup/teardown, thresholds → exit code, live TUI,
markdown report.

**Out (deferred, named in _Deferred_ below):** SSE / long-lived streaming requests, distributed
workers, protocols beyond HTTP(S).

M1 deliberately carries the assertion machinery. It could have been M2 — but every one of the four
runs needs it, so a "pure load engine" M1 would ship a tool its only customer cannot use, and would
bolt counter-merging onto a worker protocol not designed to carry it.

## Decisions specific to M1

### D1-01 — Open-loop arrivals, and latency measured from the _scheduled_ instant

The engine dispatches requests on a schedule computed in advance, independent of whether earlier
responses have come back. Closed-loop (N virtual users each awaiting its own response) was rejected
because it hides **coordinated omission**: when the target slows down, a closed-loop generator
naturally sends less, so the latency samples are drawn disproportionately from moments the system
was healthy. The reported p99 flatters the target exactly when the truth matters most. For a tool
whose pitch is _prove your numbers_, that is disqualifying.

The correction is not just open-loop dispatch; it is **where the clock starts**. Every request
records two numbers:

- `latency` — send → response. What the target took.
- `scheduledLatency` — **scheduled** dispatch instant → response. What a user waiting in line
  actually experienced, including time the generator itself was backed up.

`scheduledLatency` is the headline percentile in the report. When the generator keeps up the two are
identical; when it does not, the gap is the story and must not be hidden.

Two honesty guards fall out of this, both of them **reported, never silent**:

- **`maxInFlight` cap.** Open-loop against a dead target is unbounded memory. On breach, the request
  is _dropped_ and counted; a run with drops is annotated in the report, because its achieved rate is
  not the requested rate.
- **Schedule lag.** If a worker cannot dispatch at the scheduled instant, the delay is already inside
  `scheduledLatency`, and the run summary reports achieved vs requested rate side by side.

Arrival profiles compose as ordered stages, so one scenario expresses ramp-then-hold:

- `constantRate({ rate, duration })` — evenly spaced, not Poisson. Reproducibility beats realism for
  a report someone will paste into a README and re-run.
- `ramp({ from, to, duration })` — linear.
- `burst({ count })` — `count` requests scheduled at t=0. The namesake run.

### D1-02 — HDR-style bucketed histograms, because merge must be lossless

Percentiles are computed from a bucketed histogram with a fixed layout: exponent buckets ×
linear sub-buckets, 3 significant digits, values in µs from 1 to ~60s. Bounded memory (~27k `Int32`
counts, ~108 KB), bounded error (≤0.1% of any recorded value), and — the property that decides it —
**merging two histograms is elementwise addition**.

t-digest was rejected: its merges are approximate _and order-dependent_, so the same run merged in a
different worker-completion order yields different numbers. Exact retention was rejected as unbounded
memory. Mergeability is the constraint, and only the fixed-layout histogram makes it exact.

Values above the ceiling are clamped **and counted as overflow**, and the overflow count is printed.
A silently clamped p99 is a lie.

### D1-03 — Workers own their metrics; the main thread merges cumulative snapshots

Each worker runs a slice of the schedule and owns a private metrics registry — histograms, counters,
checks. No shared mutable state, no locks, no `SharedArrayBuffer` atomics.

Workers post **cumulative** snapshots (not deltas) on a timer for the live TUI, and a final snapshot
at the end. The main thread keeps the latest snapshot per worker and re-merges on each update. This
is idempotent: a dropped, delayed, or duplicated message cannot corrupt the aggregate, which a
delta protocol could. Bucket arrays travel as typed arrays.

Schedule splitting is deterministic: for rate `R` across `W` workers each worker generates `R/W` with
a phase offset; for `burst(N)` each worker takes `N/W` with the remainder distributed to the first
workers. Same config, same split, every run.

### D1-04 — TS config loaded by Node's native type-stripping

`stampede run scenarios.ts` imports the user's file directly — Node 24 strips types natively, so
there is no bundler, no build step, no dependency, and identical behaviour in the main thread and in
workers. All three were verified against Node v24.12 before this decision was written, including a
worker importing the config and receiving setup state through `workerData`.

The argv string is **resolved to a `file:` URL before it reaches `import()`** —
`pathToFileURL(path.resolve(arg))` — and a path that does not exist fails with `RunFailed` (exit 2).
Handing a raw argument to `import()` would also accept `data:` specifiers, which execute inline, and
bare specifiers, which resolve out of `node_modules`. Running the user's config _is_ arbitrary code
execution by design — the same trust model as a vitest or tsup config — but the specifier a user
typed as a path should only ever be read as a path. It also leaves
`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` as the single remaining config-loading error path.

The cost is real and accepted: **erasable syntax only** — no `enum`, no parameter properties, no
`namespace`. Node raises `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` with a message that names the offending
construct, so the CLI catches it and re-emits it as an actionable error pointing at the file and the
fix, rather than a stack trace. (open-ticket hit this same limit already; the constraint is known,
not discovered.)

This forces one architectural constraint worth stating plainly, because it shapes the user-facing
API: **functions cannot cross the worker boundary**, so each worker imports the config file itself.
Therefore `setup()` runs **once, on the main thread**, and its return value must be
structured-cloneable — it is data handed to every virtual user, not a live object. `teardown()`
likewise runs once on the main thread, after the storm, and is where run 1's real proof lives.

### D1-05 — Multiple scenarios per run, each with its own metric namespace

A run is a list of scenarios, not one scenario. Contract run 3 ("heavy `GET`s **while** writes
contend") is unsatisfiable otherwise, and separating read p99 from write p99 is the entire point of
that measurement. The scheduler multiplexes scenarios onto the same workers; each scenario carries
its own histograms, counters, and checks, and gets its own section in the report.

### D1-06 — Thresholds are typed predicates, not a string DSL

The non-goals say _no scripting DSL — the TS config is the DSL_. So a threshold is a named predicate
over the merged run summary:

```ts
thresholds: [
  { name: "exactly one buyer wins", assert: (s) => s.counters.reserved201 === 1 },
  { name: "no double sells", assert: (s) => s.checks.doubleSell.failed === 0 },
  { name: "read p99 under 250ms", assert: (s) => s.scenarios.reads.p99 < 250 },
];
```

Typed against the summary shape, autocompleted in the editor, no parser to write, and the `name` is
what the report and the CI failure print. Exit codes: **0** all thresholds pass · **1** a threshold
was violated · **2** the run itself failed (config error, unreachable target). CI needs to tell "your
system broke the invariant" apart from "the tool broke".

### D1-07 — Engine and TUI share nothing but an event stream

`src/engine/` imports no UI code and is exported from `src/index.ts` for programmatic use. It emits
typed events; the TUI renderer and the markdown reporter are two independent consumers of that
stream. Enforced by an ESLint boundary rule, not by good intentions.

## Shape

```
src/
├── cli.ts                 # arg parsing, exit codes — the only process.exit in the repo
├── index.ts               # programmatic entry: runs an engine, returns a summary
├── config/                # TS config loading, defineConfig types, edge validation
├── metrics/               # histogram · counters · checks · merge  (pure, no I/O)
├── engine/                # arrival profiles · scheduler · worker pool · HTTP dispatch
├── report/                # markdown renderer
└── tui/                   # live dashboard (the only consumer allowed to draw)
```

## Sub-PR breakdown

1. **docs — this design**, plus the `docs/decisions.md` entries for D1-01…D1-07.
2. **feat(metrics) — histogram, counters, checks, and their merges.** Pure and I/O-free, so it is
   tested hard: recorded quantiles within the error bound, merge is associative _and_ commutative,
   overflow counted not clamped-silently, empty-histogram edge cases.
3. **feat(engine) — arrival profiles + open-loop scheduler,** single-threaded, dispatching through a
   stub transport. Tests: a rate produces the right dispatch instants, `burst` schedules all at t=0,
   ramp is linear, `maxInFlight` drops and counts, `scheduledLatency` includes injected generator lag.
4. **feat(engine) — worker pool + snapshot protocol.** Deterministic schedule splitting, cumulative
   snapshots, main-thread merge. Tests: N workers over one schedule reproduce the single-threaded
   dispatch set; a duplicated or dropped snapshot leaves the aggregate correct.
5. **feat(config) — TS config loading + setup/teardown.** `defineConfig`, edge validation of the
   loaded object, the `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` translation, setup state to `workerData`.
6. **feat(cli) — `stampede run`, threshold evaluation, exit codes.**
7. **feat(report) — markdown report.** Scenario, throughput, percentile table, checks table.
8. **feat(tui) — live dashboard.** Consumes the same event stream as the reporter.
9. **docs — README + the reality-gate evidence.**

## Verify for real (gate two)

Green tests do not prove a load tester. A load tester is proven by pointing it at a server whose
behaviour is already known and checking that it tells the truth.

- **Known-latency target.** A local server that sleeps exactly 50ms: reported p50 must land on ~50ms.
  If the instrument cannot measure a stopwatch, nothing else it says counts.
- **Achieved rate = requested rate** against a fast target, measured independently of the tool's own
  accounting.
- **The honesty test — the one that matters.** A target deliberately slower than the requested rate
  (fixed 200ms delay, rate well above its capacity). The tool must report climbing
  `scheduledLatency`, an achieved rate below the requested one, and any drops — _not_ a flattering
  p99 obtained by quietly throttling itself. This is the coordinated-omission failure mode, and
  demonstrating stampede does not have it is the reason D1-01 exists.
- **The namesake run, end to end**, against a local open-ticket: N buyers, one seat, exactly one 201,
  and a teardown that re-reads the seat map and finds exactly one seat sold. Read-only use of
  open-ticket — M5 is a separate track.

## Deferred (not M1)

- **SSE / long-lived streaming requests** (open-ticket's scenario 5, M+ concurrent subscribers).
  Needs a streaming request mode rather than request/response — a later milestone, and open-ticket
  is explicitly not blocking on it.
- Poisson arrivals, distributed workers, protocols beyond HTTP(S), a cloud service, and everything
  else the non-goals say no to on purpose.
